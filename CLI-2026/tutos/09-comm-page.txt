# Tutorial 9: COMM Page — Domain Communication Buffer
# =====================================================
# Demonstrates the COMM attribute: a parent-owned shared memory page bound to
# a child domain's VP.  The monitor can read/write the page on behalf of the
# child's VP (e.g. for ThemIC intercept messages, event flags, etc.).

@msg ━━━ Tutorial 9: COMM Page — Domain Communication Buffer ━━━
@msg
@msg A COMM page is parent-owned memory bound to a child domain's VP.
@msg   • Registered by the parent via register-comm <mem> <child> <vp_id>
@msg   • NOT mapped in the child's EPT — only the monitor (capavisor) accesses it
@msg   • Multiple COMM pages per child domain are allowed
@msg   • Implies CLEAN (zeroed on revoke); does NOT imply VITAL
@msg   • Cannot be carved, aliased, or sent while the binding is active
@msg

# ── Step 1: Initialize ────────────────────────────────────────────────────────
@msg 📋 Step 1: Initialise root domain with 256 KB of memory
init root 0x40000

@msg

# ── Step 2: Create a child domain ─────────────────────────────────────────────
@msg 📋 Step 2: Create a child domain
create-domain root child 0b1111 all
seal child

@msg
@msg ✓ 'child' is sealed
@msg

# ── Step 3: Carve the COMM page from root's RAM ──────────────────────────────
@msg 📋 Step 3: Carve a 4 KB COMM buffer from root's memory
@msg
@msg The COMM page must be:
@msg   • Carved (not aliased) — exclusive derivation chain required
@msg   • Exclusive status (no alias in its ancestry)
@msg   • Owned by the registering domain (the parent)
carve r0 comm0 0x0 0x1000 rw

@msg
@msg ✓ 'comm0' carved: kind=Carve, status=Exclusive, rights=RW
@msg

# ── Step 4: Register the COMM page bound to child VP 0 ───────────────────────
@msg 📋 Step 4: Register comm0 as a COMM page for child's VP 0
@msg
@msg After this call:
@msg   • comm0 carries COMM|CLEAN (not VITAL)
@msg   • The monitor receives a CommRegion update with target_domain_id and vp_id
@msg   • The page is NOT in child's EPT — only the monitor maps it
register-comm comm0 child 0

@msg
@msg ✓ CommRegion update emitted: monitor now maps the COMM page
@msg

# ── Step 5: Inspect the registered COMM cap ──────────────────────────────────
@msg 📋 Step 5: List all capabilities — comm0 now shows COMM|CLEAN
list

@msg

# ── Step 6: Multiple COMM pages allowed ──────────────────────────────────────
@msg 📋 Step 6: Register a second COMM page for the same child (VP 1)
@msg
@msg Unlike the old one-shot design, multiple COMM pages are allowed.
carve r0 comm1 0x1000 0x1000 rw
register-comm comm1 child 1

@msg
@msg ✓ Second COMM page registered for VP 1
@msg

# ── Step 7: Re-registering the same cap is rejected ──────────────────────────
@msg 📋 Step 7: Re-registering a cap that already has COMM must fail

# EXPECT_FAIL
register-comm comm0 child 0

@msg
@msg ✗ InvalidOperation — capability already carries the COMM attribute
@msg

# ── Step 8: Forbidden derivations on a COMM cap ──────────────────────────────
@msg 📋 Step 8: Carve, alias, or send of a COMM cap must be rejected

# EXPECT_FAIL
carve comm0 bad_carve 0x0 0x100 r

@msg
@msg ✗ PermissionDenied — COMM regions cannot be carved

# EXPECT_FAIL
alias comm0 bad_alias 0x0 0x100 r

@msg
@msg ✗ PermissionDenied — COMM regions cannot be aliased
@msg

# ── Step 9: Revocation — COMM does not kill owning domain ────────────────────
@msg 📋 Step 9: Revoke comm0 from root
@msg
@msg Two updates are produced (no RevokeDomain — COMM is not VITAL):
@msg   1. UncommRegion — monitor unmaps its access to the COMM page
@msg   2. ZeroMemory   — physical range zeroed (CLEAN)
revoke r0 comm0

@msg
@msg ✓ Monitor unmapped COMM page. Memory zeroed. Root domain is still alive.
@msg

# ── Step 10: Final state ──────────────────────────────────────────────────────
@msg 📋 Step 10: Final state — root is alive, child is still alive
list

@msg
@msg 📖 Key Takeaways:
@msg   • COMM is parent-owned memory bound to a child domain's VP
@msg   • Registered with register-comm <mem> <child> <vp_id>
@msg   • NOT mapped in child EPT — only monitor accesses it via HHDM
@msg   • Multiple COMM pages per child are allowed (one per VP, or more)
@msg   • Implies CLEAN (zero on revoke) but NOT VITAL (domain survives)
@msg   • Bindings auto-release when the child domain is revoked
@msg
@msg 💡 Use case: ThemIC pages (intercept messages, event flags, doorbell
@msg    tables) are COMM pages bound to child VPs.
@msg
