# Domain Capabilities

## The Domain Type

A domain is an execution environment with a unique identity, a lifecycle, and a policy that constrains what it may do. Domains form their own CDT subtree (separate from the memory CDT).

```
Domain {
    id:                    u64              (globally unique, auto-incremented)
    status:                DomainStatus     (Unsealed | Sealed | Revoked)
    policy:                DomainPolicy
    memory_capabilities:   BTreeMap<LocalHandle, CapabilityWeak<MemoryRegion>>
    domain_capabilities:   BTreeMap<LocalHandle, CapabilityWeak<Domain>>
    pending_capabilities:  BTreeMap<u64, PendingCapability>
}
```

## Domain Lifecycle

```
            create_child_domain()
                    │
              ┌─────▼──────┐
              │  Unsealed   │  ← capabilities can be configured, policy set
              └─────┬───────┘
                seal()│
              ┌─────▼──────┐
              │   Sealed    │  ← domain is executable; most config is frozen
              └─────┬───────┘
           revoke() │
              ┌─────▼──────┐
              │  Revoked    │  ← domain is dead; all capabilities invalidated
              └────────────┘
```

- **Unsealed**: the domain is being configured. Capabilities can be carved/aliased into it. The domain cannot run.
- **Sealed**: the domain is frozen and executable. It can now invoke MonitorAPI operations (subject to its policy). Most configuration changes are rejected.
- **Revoked**: the domain and all its descendants have been torn down. Any `CapabilityRef` pointing into a revoked subtree is invalid.

Transitions are one-way: `Unsealed → Sealed → Revoked`. There is no un-sealing or un-revoking.

## DomainPolicy

The policy is immutable after sealing. It encodes the domain's authority:

### Core Bitmap

```rust
pub cores: u64   // bit i = 1 means core i may run this domain
```

A domain can only execute on a core if the corresponding bit is set. Validated by `SwitchManager` at switch time.

### Monitor API

```rust
pub api: MonitorAPI   // 13-bit bitmap
```

Operations a domain is permitted to invoke on the monitor:

| Constant | Meaning |
|----------|---------|
| `CREATE` | Create child domains |
| `SET` | Configure capabilities |
| `GET` | Inspect capabilities |
| `SEND` | Transfer capabilities to other domains |
| `SEAL` | Seal child domains |
| `ATTEST` | Generate attestation reports |
| `ENUMERATE` | Walk the domain subtree |
| `SWITCH` | Switch execution to a child or parent |
| `ALIAS` | Create aliased memory children |
| `CARVE` | Create exclusive memory children |
| `REVOKE` | Revoke child capabilities |
| `GETCHAN` | Obtain communication channels |
| `RECEIVE_AFTER_SEAL` | Accept capability transfers after sealing (see below) |

A child domain's `MonitorAPI` must be a *subset* of its parent's (`MonotonicityViolation` otherwise).

### Interrupt Policy

```rust
pub interrupts: InterruptPolicy {
    default: VectorPolicy,
    overrides: BTreeMap<u8, VectorPolicy>,
}
```

Each interrupt vector is governed by a `VectorPolicy`:

```rust
pub struct VectorPolicy {
    pub visibility: InterruptVisibility,  // Deliver | Report | NotReport
    pub read_set:   u64,   // bitmask of registers readable during handling
    pub write_set:  u64,   // bitmask of registers writable during handling
}
```

- **Deliver**: the interrupt is delivered directly to this domain.
- **Report**: the domain is notified (reported to) but the interrupt walks up to the parent.
- **NotReport**: the domain is invisible to this interrupt; routing continues up the CDT.

### Virtual Processor States

```rust
pub vprocessor_states: Vec<VProcessorState>
```

Platform-specific register contexts (general-purpose registers, platform data) that the domain may occupy. Each state has a unique `id`.

## Pending Capabilities (`RECEIVE_AFTER_SEAL`)

Normally, once a domain is sealed its capability set is frozen — no new capabilities can be installed. The `RECEIVE_AFTER_SEAL` API flag lifts this restriction:

1. Another domain calls `send` targeting a sealed domain with `RECEIVE_AFTER_SEAL`.
2. The capability is placed in the target domain's `pending_capabilities` map with a fresh pending ID.
3. The target domain (now running) later calls:
   - `accept_pending_capability(pending_id, handle)` — activates the capability under `handle`.
   - `reject_pending_capability(pending_id)` — discards it.

This mechanism allows safe post-seal resource sharing without breaking the sealed-domain invariant for capabilities the domain has not yet explicitly accepted.

## Root Domain

The root domain is the trust anchor of the whole system:

- `id = 0` (reserved; never generated by `generate_domain_id()`)
- Created `Sealed` — it is always executable.
- Policy: `MonitorAPI::ALL`, all cores enabled.
- Has no parent in the CDT; it is the root of the domain tree.

All other domains must be derived (directly or indirectly) from the root domain.
